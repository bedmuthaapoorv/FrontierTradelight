# Backtesting and Calibrating Event-Driven Trading Signals: Methodology for Per-Event-Type Outcome Distributions

## Standard event-study methodology for building a historical library of abnormal returns per event type (data requirements, benchmark choice, small-sample handling)

### Takeaway
The canonical event-study framework (MacKinlay 1997) — define event date, estimation window, event window, compute abnormal returns via a market model fit over a pre-event estimation window, then aggregate into cumulative abnormal returns (CAR) — is the right skeleton for a per-event-type library, but it needs explicit small-sample adaptations (fewer, more robust test statistics; pooled/aggregate cross-sectional variance; shorter, high-conviction event windows) because contract-win-style events are rare per stock.

### Cited Findings
- MacKinlay (1997) frames the event study as using financial market data to measure a specific event's economic impact on firm value, on the premise that under market rationality the event's effect is reflected immediately in prices, so a relatively short window of price data suffices — general procedure: define the event, identify the event window, measure abnormal returns, and run statistical tests. — [Event study (Wikipedia summary of MacKinlay)](https://en.wikipedia.org/wiki/Event_study)
- Abnormal return = actual return − normal (expected) return, where "normal" is modeled via one of three approaches: the market model (regression of stock return on a market/index return over a prior estimation window, typically ~120 days, to get alpha/beta/residual variance), CAPM, or the simpler mean-adjusted-returns model. — [Event study (Wikipedia)](https://en.wikipedia.org/wiki/Event_study)
- Standard significance testing divides the abnormal return by the market-model regression's root-mean-square error and compares to a Student's t critical value. — [Event study (Wikipedia)](https://en.wikipedia.org/wiki/Event_study)
- A known pitfall: during high-volatility regimes (e.g., 2008 crisis) the standard t-test flags too many firms as "abnormal," since market-model residual variance from a calm estimation window under-fits volatile-period noise; short-horizon event studies are considered materially more reliable than long-horizon designs. — [Event study (Wikipedia)](https://en.wikipedia.org/wiki/Event_study)
- Dedicated research on small samples: "Small sample size problems and the power of the test in the event study methodology" investigates, via simulation, how test statistics/model choice (mean-adjusted returns, market-adjusted returns, market model) interact with small samples and market index choice to affect statistical power and Type-I error. — [Small sample size problems and the power of the test in event study methodology (ResearchGate)](https://www.researchgate.net/publication/291886220_Small_sample_size_problems_and_the_power_of_the_test_in_the_event_study_methodology)
- In rare-event statistics generally, increasing the *overall* sample size does not raise power if the number of actual rare-event occurrences stays fixed — power is governed by the count of events, not total observation count; the standard remedy in case-control/rare-event designs is to add more "control" (non-event) observations per case rather than chasing more raw data. — [Do more observations bring more information in rare events? (arXiv)](https://arxiv.org/pdf/2506.13671); [Rare events sample size discussion](https://win-vector.com/2013/12/03/sample-size-and-power-for-rare-events/)
- For corporate contract announcements specifically (a directly analogous event type to the "PSU defense contract-win" case), academic literature confirms contract-win announcements are a distinct, "scarcely studied" corporate event category, and that winning contractors experience a positive average stock market reaction — establishing this as a legitimate, separately-classed event type warranting its own abnormal-return library rather than being lumped with generic "good news." — [The Valuation Effect and Determinants of Corporate Contracting, UCLA Anderson working paper](https://www.anderson.ucla.edu/documents/areas/fac/finance/20-05.pdf) (PDF; full statistical detail not extractable via automated fetch — recommend manual read for exact CAR figures)
- For M&A-style events (structurally similar large-news events), typical event windows are narrow: ±10 days (21-day window) is common, but tighter windows like [-1,+1] are preferred in some designs because wider windows such as [-2,+2] add noise and *weaken* forecasting accuracy; the market's reaction is often "complete by the day after the announcement," with most of the return realized immediately around the event date. — [Predicting Stock Returns Around M&A Announcements](https://www.tandfonline.com/doi/full/10.1080/15427560.2025.2563883); [Event Studies in M&A Research (EventStudyTools)](https://www.eventstudytools.com/mergers-acquisitions)
- Existing empirical literature already documents heterogeneity in post-event CAR distribution *shape* by event category: risk-related events (e.g., "Risk Warning," "Violation") show wider, heavier-tailed distributions (higher uncertainty), while routine events (e.g., dividend, industry announcements) show tighter distributions concentrated near zero — direct empirical support for maintaining separate distributions per event type rather than one pooled distribution. — [Trade the Event: Corporate Events Detection for News-Based Event-Driven Trading (arXiv 2105.12825 / ACL Findings 2021)](https://arxiv.org/pdf/2105.12825)
- The same "Trade the Event" work introduces the EDT (Event-Driven Trading) dataset: 9,721 news articles with token-level event-type annotations, and for each labels open/close at the first tradeable minute plus high/low and close prices at 1/2/3 trading days after — i.e., a concrete data schema for building a per-event, per-horizon outcome table (a close structural analogue to what would need to be built for the PSU-contract use case). — [Trade the Event (arXiv)](https://arxiv.org/pdf/2105.12825), [ar5iv HTML version](https://ar5iv.labs.arxiv.org/html/2105.12825)

### Inferences
- For a rare event type at the single-stock level (e.g., "PSU defense contract win" for one ticker), the estimation window/market-model machinery from MacKinlay is still usable for computing each individual instance's abnormal return, but statistical significance testing per stock will be underpowered — the practical fix (per the rare-event power literature) is to pool across many *instances* of the same event type (across stocks/sectors, i.e., more "cases") rather than trying to lengthen the time-series for one stock.
- A defensible default architecture: (1) fixed short event window (e.g., -1 to +5 or +10 trading days) computed via market-model abnormal returns against a broad index or sector index; (2) per-instance CAR time path stored, not just the terminal CAR, so days-to-peak / days-to-50%-reversion can be derived from the same records; (3) explicit event-type taxonomy (e.g., separate "contract win" from generic "positive news") since the literature shows distribution shape differs meaningfully by type.

## Constructing summary statistics per event-type bucket (median CAR, IQR, win rate, days-to-peak, days-to-50%-reversion) and handling small samples robustly (shrinkage / Bayesian pooling)

### Takeaway
The James–Stein / empirical-Bayes shrinkage framework is the standard, well-established statistical tool for exactly this problem — pulling a noisy, small-sample per-stock (or per-stock-per-event-type) estimate toward a more reliably-estimated group mean (sector, or same event-type-across-all-stocks) — and it is provably better than either the naive single-stock estimate or full pooling, for 3+ groups being estimated jointly.

### Cited Findings
- The James–Stein estimator dominates the maximum-likelihood (i.e., naive sample-mean) estimator under squared-error loss whenever three or more group means are being estimated jointly, and it has a rigorous empirical-Bayes derivation (Efron & Morris): individual group observations are modeled as normal around unknown group means, which are themselves drawn from a normal "prior" distribution across groups, with that prior's parameters estimated from the data itself (i.e., estimated empirically, not chosen a priori). — [The James-Stein Estimator (Berkeley course notes)](https://stat210a.berkeley.edu/fall-2024/reader/jamesstein.html); [Chapter 7, James–Stein Estimation and Ridge Regression, Efron & Hastie "Computer Age Statistical Inference"](https://efron.ckirby.su.domains/other/CASI_Chap7_Nov2014.pdf)
- The estimator "manages to estimate the correct amount of shrinkage from the data" so it avoids over-shrinking most of the time, improving mean-squared error for any true parameter configuration; it is "surprisingly good even without making any Bayesian assumptions at all," and is used broadly in hierarchical modeling and "high-dimensional signal recovery where many related quantities must be estimated from limited data" — a direct description of the per-stock/per-event-type estimation problem. — [The James-Stein Estimator (Berkeley)](https://stat210a.berkeley.edu/fall-2024/reader/jamesstein.html)
- Modern hierarchical Bayesian partial pooling (the generalization of James-Stein to more flexible models, typically fit via Stan/brms/PyMC) "shrinks each group's estimate toward the overall mean by an amount set by its own sample size and the between-group variance — beating both no pooling and complete pooling," and is explicitly used in finance for equity factor-beta estimation where per-stock samples are short/noisy, with the benefit that "sector membership is more informative for some exposures than others" — i.e., the degree of sector-pooling should itself be estimated/tuned, not fixed. — [Hierarchical Partial Pooling for Repeated Binary Trials (Stan case study)](https://mc-stan.org/learn-stan/case-studies/pool-binary-trials.html); [equity factor-beta hierarchical Bayes project](https://github.com/tonykark1/hierarchical-bayesian-); [How to Fit Hierarchical Bayesian Models in R with brms (R-bloggers)](https://www.r-bloggers.com/2026/03/how-to-fit-hierarchical-bayesian-models-in-r-with-brms-partial-pooling-explained/)
- The classic worked demonstration of this exact "small sample per unit, shrink toward group" pattern is baseball batting-average empirical Bayes estimation ("in-season prediction of batting averages"), a widely-cited template for shrinkage estimation with binomial/win-rate-like statistics under small samples — directly analogous to estimating a per-stock "win rate" (fraction of historical event instances with a positive CAR) from only a handful of observed instances. — [In-season prediction of batting averages: empirical Bayes and Bayes field test (arXiv)](https://arxiv.org/pdf/0803.3697)
- Empirical event-study evidence independently supports bucketing by event type before any cross-sectional statistic is computed, since different event types show materially different CAR distribution dispersion and tail shape (see prior section) — meaning naive pooling of "PSU defense contract win" with an unrelated event type would bias the summary statistics for both. — [Trade the Event (arXiv 2105.12825)](https://arxiv.org/pdf/2105.12825)

### Inferences
- A workable hierarchy for the described system: level 1 = specific stock × specific event-type (fewest observations, noisiest); level 2 = sector × event-type (e.g., all PSU defense names' contract-win reactions); level 3 = event-type only (broadest, most stable). Shrinkage/partial pooling should blend level 1 toward level 2, and level 2 toward level 3, with the blending weight determined empirically by relative sample sizes and between-group variance at each level (exactly the James-Stein / hierarchical Bayes recipe), rather than a fixed manual weight.
- Win rate (a proportion) is naturally suited to Beta-Binomial empirical Bayes shrinkage (Beta prior updated with successes/failures) rather than Normal-based James-Stein, since it's bounded in [0,1] — the batting-average precedent above uses exactly this. Median CAR / days-to-peak / days-to-reversion (continuous, skewed statistics) are better shrunk using a Normal (or Normal after rank/log transform, since these are typically medians reported specifically to be robust to skew) hierarchical model.
- IQR-based robustness (using interquartile range instead of standard deviation, and median instead of mean) is well-motivated independent of the shrinkage question, because event-study CAR distributions are documented as heavy-tailed for some event types (see risk-event finding above) — robust statistics reduce the influence of one extreme historical instance dominating a small-sample bucket.

### Gaps
- No source found giving a ready-made formula for shrinking a *duration* statistic (days-to-peak, days-to-50%-reversion) specifically — the literature located covers shrinkage of return/magnitude statistics (means, proportions) far more than shrinkage of timing statistics. This would likely need to be adapted by treating "days to peak" as a bounded/discrete quantity and applying the same Normal or Beta-Binomial-style empirical Bayes logic ad hoc, since no direct precedent was found.
- Could not verify a specific finance paper that shrinks event-study CARs directly via James-Stein/hierarchical Bayes (the finance-specific hits found were for equity factor betas, not event-study abnormal returns) — the mapping from the general shrinkage literature to this specific event-study application is an inference, not a directly cited finance-event-study source.

## Bayesian updating / online-learning methods for updating expected-return and expected-duration distributions as new event instances occur

### Takeaway
Conjugate Bayesian updating (Normal-Inverse-Gamma for a return-like variable with unknown mean and variance) gives exact, cheap-to-compute closed-form posterior updates after each new event instance, while EWMA gives a simpler non-Bayesian alternative for online tracking that naturally down-weights stale/older regime data; conformal prediction can be layered on top of either to produce distribution-free uncertainty bounds, though it requires care in a time-series (non-exchangeable) setting.

### Cited Findings
- The Normal-Inverse-Gamma (NIG) distribution is the conjugate prior for a normal distribution with unknown mean *and* unknown variance: an (unconditional) inverse-gamma prior on the variance, and, conditional on that variance, a normal prior on the mean — exactly the situation of not knowing either the expected magnitude or the volatility of an event-type's CAR in advance. — [Normal-Inverse-Gamma conjugate prior discussion](https://dirknbr.medium.com/a-simple-bayesian-rl-with-normal-inverse-gamma-updates-f00977cd0beb)
- "The incremental version of Bayesian estimation updates a node's prior Normal-Inverse-Gamma pdf by data weighted according to specified rules," enabling real-time posterior updates as new observations arrive — i.e., after each new contract-win instance for a stock/sector, the NIG posterior can be updated in closed form without refitting from scratch. — [Bayesian RL with Normal-Inverse-Gamma updates (Medium)](https://dirknbr.medium.com/a-simple-bayesian-rl-with-normal-inverse-gamma-updates-f00977cd0beb)
- EWMA is a recursive estimator assigning exponentially decaying weight to past observations, foundational to "real-time monitoring, volatility forecasting, adaptive modeling, and online learning algorithms"; the decay parameter λ controls memory length — RiskMetrics (J.P. Morgan) popularized λ = 0.94 for daily-return volatility as an industry-standard default. — [EWMA overview (EmergentMind)](https://www.emergentmind.com/topics/exponentially-weighted-moving-average); [EWMA for Systematic Trading (RobotWealth)](https://robotwealth.com/using-exponentially-weighted-moving-averages-to-navigate-trade-offs-in-systematic-trading/)
- More general "Exponentially Weighted Moving Models" (a 2024 paper by Luxenberg & Boyd, Stanford) formalize EWMA as fitting a model to minimize an exponentially time-weighted loss, generalizing the basic moving-average update to arbitrary online-fit statistics — a useful generalization beyond just mean/variance tracking to more model classes. — [Exponentially Weighted Moving Models (arXiv/Stanford)](https://web.stanford.edu/~boyd/papers/pdf/ewmm.pdf)
- Conformal prediction (CP) is a distribution-free framework producing prediction sets/intervals with guaranteed coverage probability, built by calibrating a model's outputs against past data; in a financial-decision context, this is used to size positions — allocating more capital to trades with narrow/reliable prediction sets and pulling back on trades with wide/uncertain ones. — [Conformal prediction in financial markets (Tildee/MAPIE writeup)](https://www.tildee.com/harnessing-conformal-forecasting-in-financial-markets-quantifying-uncertainty-and-managing-risk-with-mapie/)
- A key caveat: standard conformal prediction assumes exchangeability (order doesn't matter) between calibration and test points, which is "fundamentally violated" in time series data due to temporal dependence and distributional shift; "Temporal Conformal Prediction" (TCP) is an adaptive variant designed specifically to restore valid coverage under this violation, and recent work argues for treating calibrated *uncertainty* estimation (rather than raw return-level point prediction) as the more stable, economically meaningful objective in non-stationary financial settings. — [A Gentle Introduction to Conformal Time Series Forecasting (arXiv 2511.13608)](https://arxiv.org/html/2511.13608v1); [Attention-Based Feature Online Conformal Prediction for Time Series (arXiv 2511.15838)](https://arxiv.org/pdf/2511.15838)

### Inferences
- A practical combined design for the described system: maintain a NIG posterior per event-type bucket (giving exact, closed-form updates of expected CAR magnitude and its uncertainty each time a new instance is confirmed), while separately using conformal calibration (ideally a time-series-aware variant, given the exchangeability caveat) on top of that posterior's point predictions to produce empirically-validated coverage intervals for realized outcomes — this hedges against the NIG model's normality assumption being wrong for heavy-tailed event types.
- EWMA is the pragmatic fallback when a fully Bayesian NIG implementation is overkill for the initial build: it requires no closed-form derivation, handles regime drift naturally via the decay parameter, and is the de facto industry standard for volatility-style statistics (RiskMetrics precedent), though it is not naturally suited to updating a discrete/count-like statistic such as win rate (for which Beta-Binomial Bayesian updating, noted in the prior section, is the more natural fit and is equally simple to implement in closed form).

### Gaps
- No source found specifically applying Bayesian/conformal updating to a *duration* variable (days-to-peak, days-to-reversion) as opposed to a return-magnitude variable — this is a genuine methodological gap; the closest applicable framework would be treating duration as a right-skewed positive variable (candidates: log-normal + conjugate normal-on-log-duration, or a survival-analysis / hazard-based updating approach), but no specific paper describing this for trading-signal calibration was found in this pass.
- Did not find a paper directly combining conformal prediction with an explicit Bayesian conjugate-prior signal-calibration pipeline (as opposed to conformal wrapping a general ML forecast) — the synthesis of "NIG posterior + conformal calibration" above is an inference from combining two separate literatures, not a directly cited joint methodology.

## Practitioner event-driven backtesting framework architecture and common pitfalls (Zipline, backtrader, QuantConnect/LEAN)

### Takeaway
All three major event-driven frameworks share the same core pattern — a data feed pushes time-ordered bars/events into per-bar callback methods (`handle_data`/`next`/`OnData`) so that strategy code only ever sees information available up to that point in time — and the literature repeatedly flags the same three failure modes: look-ahead bias, survivorship bias from index-membership backfilling, and (for vectorized alternatives) the loss of realism that event-driven engines exist specifically to avoid.

### Cited Findings
- Zipline is described as "a Pythonic event-driven system for backtesting," originally the backtesting/live-trading engine behind Quantopian, structured around `initialize()` and `handle_data()`/`handle_data` callback functions, plus a separate Pipeline API for cross-sectional universe selection and factor ranking; a documented tradeoff is that per-bar Python execution makes it slow for large universes or minute-level data. — [Battle-Tested Backtesters comparison (Medium)](https://medium.com/@trading.dude/battle-tested-backtesters-comparing-vectorbt-zipline-and-backtrader-for-financial-strategy-dee33d33a9e0); [Zipline 3.0 docs](https://zipline.ml4trading.io/)
- Backtrader processes each bar sequentially and dispatches to strategy methods like `next()`, `notify_order()`, and `notify_trade()` "as events occur," which is described as intuitive specifically for strategies that need to react to unfolding conditions (a natural fit for event-driven signals like contract-win announcements). — [Python Backtesting Framework comparison (QuantEngines)](https://quantengines.com/blog/python-backtesting-framework)
- QuantConnect/LEAN is explicitly "event-driven," with modular, pluggable components: an `IDataFeed` (reads from disk in backtests, streams live in production), an `ITransactionHandler` (processes orders through fill models or a real brokerage), and an `IRealtimeHandler` (emits real-time events like end-of-day); the primary event handler is `OnData`, triggered "sequentially at the point in time the data is available; in backtesting and live" — i.e., the framework's core guarantee is temporal ordering parity between backtest and live paths. — [Algorithm Engine docs (QuantConnect)](https://www.quantconnect.com/docs/v2/writing-algorithms/key-concepts/algorithm-engine); [Event Handlers docs (QuantConnect)](https://www.quantconnect.com/docs/v2/writing-algorithms/key-concepts/event-handlers)
- Vectorized backtesters (e.g., VectorBT) are faster than event-driven ones by processing whole arrays at once rather than iterating bar-by-bar, but this is explicitly framed as a speed/realism tradeoff, since event-driven backtesters are "much more akin to live-trading infrastructure" and hence produce a smaller backtest-vs-live performance gap. — [Battle-Tested Backtesters comparison (Medium)](https://medium.com/@trading.dude/battle-tested-backtesters-comparing-vectorbt-zipline-and-backtrader-for-financial-strategy-dee33d33a9e0)
- Look-ahead bias is defined as a backtest incorporating information "that would not have been available at the time a trading decision was made"; unlike overfitting/data-snooping (which degrade performance gradually), look-ahead bias produces results that are "fundamentally fictitious," with the gap between backtest and live results appearing "immediate and catastrophic" upon deployment. — [Look-Ahead Bias in Backtesting (Algorier)](https://algorier.com/blog/look-ahead-bias-in-backtesting/)
- Survivorship bias is defined as backtests including only currently-active names while excluding delisted/bankrupt ones, which "systematically overstates returns and understates risk"; a specific, commonly-missed variant is evaluating a strategy over a long historical span using only the *current* (e.g., 2025) constituents of an index, which implicitly builds in look-ahead bias by removing names that were delisted or went bankrupt along the way. — [Look-Ahead-Freedom as Temporal Non-Interference (arXiv 2607.04958)](https://arxiv.org/pdf/2607.04958); [Problems in Backtesting and Biases in Data (AnalystPrep/CFA)](https://analystprep.com/study-notes/cfa-level-2/problems-in-backtesting/)
- Recommended prevention practice: process observations "exactly as they occurred," ensure future information never influences earlier decisions, and use point-in-time datasets that preserve what was actually knowable on each historical date rather than later-revised data (e.g., restated financials, post-hoc index membership). — [Problems in Backtesting and Biases in Data (AnalystPrep)](https://analystprep.com/study-notes/cfa-level-2/problems-in-backtesting/); [Look-Ahead-Freedom paper (arXiv)](https://arxiv.org/pdf/2607.04958)

### Inferences
- For the specific use case (per-event-type statistical library, not a full continuous trading strategy), a lightweight event-driven harness is more appropriate than adopting a full framework like LEAN — the essential architectural lesson to borrow is the point-in-time discipline: every historical event instance used to build the outcome distribution must be timestamped with when the announcement information was actually public (not adjusted/restated after the fact), and the estimation window for each instance's abnormal-return baseline must only use data strictly prior to the event date.
- Event clustering/overlap (an explicitly named risk in the assignment brief) was not directly documented in the sources retrieved this pass; the closest documented analog is that overlapping/wide event windows are known to add noise and weaken effect measurement (see M&A section above) — clustering (e.g., multiple contract-win announcements for the same stock in a short window, or sector-wide news affecting many stocks the same day inflating cross-sectional correlation of "abnormal" returns) is a known general event-study concern but not separately sourced here.

### Gaps
- Did not find a source directly and explicitly using the term "event clustering" in event-study or backtesting contexts within this search pass; the general event-study literature is known to address cross-sectional correlation of abnormal returns when many events cluster on the same calendar dates (this inflates apparent statistical significance if standard errors assume independence), but a specific citation for this exact pitfall was not retrieved and should be flagged as needing another research pass (e.g., search directly for "cross-sectional correlation event clustering Brown Warner" or "event date clustering test misspecification").
- Brown & Warner (1985) and Kothari & Warner were named as suggested sources in the brief but were not directly retrieved in this pass (search budget was allocated to newer/practical sources instead) — recommend a follow-up fetch of Brown & Warner (1985), "Using Daily Stock Returns: The Case of Event Studies," Journal of Financial Economics, for the classical treatment of cross-sectional dependence and clustering.

## Existing open-source or documented systems combining event classification + historical outcome distribution lookups

### Takeaway
The most directly relevant reference architecture found is the "Trade the Event" research system (arXiv 2105.12825 / EDT dataset), which pairs a corporate-event-type classifier with a labeled historical outcome table (per-event price/return labels at multiple horizons); this is architecturally very close to the target system (event classification → per-event-type historical outcome lookup) but is an academic research artifact/dataset rather than a production trading system, and no fully-documented production-grade open-source system doing exactly "event classification + per-bucket historical outcome distribution + live signal calibration" was found.

### Cited Findings
- "Trade the Event: Corporate Events Detection for News-Based Event-Driven Trading" (arXiv 2105.12825, ACL Findings 2021) introduces the EDT dataset: 9,721 news articles with token-level corporate-event-type annotations, explicitly built as a benchmark for text-based stock prediction; each article carries price labels — open/close at the first tradeable minute, plus high/low and close prices at 1, 2, and 3 trading days after the event — giving a ready template for a "per-event-instance, multi-horizon outcome record" schema. — [Trade the Event (arXiv)](https://arxiv.org/pdf/2105.12825); [ACL Findings PDF](https://aclanthology.org/2021.findings-acl.186.pdf)
- The described news-trading pipeline pattern generally: (1) identify a trading signal/event/sentiment from news text, (2) resolve the related company/ticker, (3) pull stock price data around the news publication time, (4) apply a transaction policy based on that signal — a four-stage pipeline directly analogous to what the target system needs (classify → look up historical distribution for that event-type/ticker → decide position sizing/duration based on that distribution). — [Trade the Event (arXiv)](https://arxiv.org/pdf/2105.12825)
- A smaller open-source project, "news-signal" (GitHub, harveybc), performs local/typed news feature extraction emitting relevance, event type, and financial tone, explicitly built "for auditable shadow-trading research," with broker integration "planned" — a lightweight, non-academic open-source precedent for the event-classification half of the pipeline, though it does not appear to include the historical-outcome-distribution/calibration half. — [harveybc/news-signal (GitHub)](https://github.com/harveybc/news-signal)
- General-purpose open-source algorithmic trading platforms (e.g., NautilusTrader) exist as production-grade event-driven execution engines, but the search did not surface documentation of them shipping a built-in "per-event-type historical outcome distribution" module — they provide the event-driven execution/backtesting substrate on which such a module could be built, not the module itself. — [NautilusTrader](https://nautilustrader.io/)

### Inferences
- No turnkey open-source system was found that does exactly what is being described (event classification feeding a maintained, per-event-type/per-stock statistical distribution of return magnitude *and* duration, Bayesian-updated over time) — this appears to be a genuine build-it-yourself gap rather than something to adopt off the shelf. The closest components to reuse/study are: the EDT dataset's outcome-labeling schema (for how to structure the historical outcome table) and a standard event-driven execution engine (LEAN/backtrader/NautilusTrader) as the substrate for point-in-time-correct backtesting of any resulting signal.
