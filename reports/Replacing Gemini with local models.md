# Replace Gemini with rules, not a laptop model

FrontierTradelight can drop Google Gemini, but this laptop should not be the place that replaces it with a local LLM. Gemini has exactly one job in the app: compiling the plain-English `rules.md` and `exit_rules.md` specs into Python (`evaluate_stock`, `select_strategy`, `resolve_exit` and `describe_state`). The models that could plausibly match or beat `gemini-3.1-flash-lite` at that job are 14–19 GB downloads. The machine has 16 GB of RAM (about 6 GB free), only an integrated GPU, about 10 GB free on C:, and no local LLM tooling. The 7–8B models that do fit would take roughly 5–10 minutes per generation, and they are likely to be less accurate than a hosted model that already shipped four off-by-one or wrong-bar bugs. The option that removes the dependency and also removes that bug class is deterministic: rule files in YAML with a small expression grammar, an interpreter with one fixed bar-offset convention, a registry of hand-written and unit-tested detectors (cup-and-handle anchors, parabola R², swing highs), and one tested `resolve_exit` engine driven by config. Its cost is real. Plain-English authoring goes away unless an LLM-to-DSL authoring aid is kept, and every new custom algorithm needs hand-written Python. Whichever path the owner picks, the guardrails described below should be built first, this week. They are what actually catch off-by-one bugs, and a provider-agnostic client layer turns "Gemini or local" into a config setting instead of a rewrite.

## Gemini compiles specs into code that nobody checks

Every LLM call in the repo goes to `gemini-3.1-flash-lite` at `temperature=0.0`. None of the calls sets a timeout, a system instruction, structured output or a token limit. The calls come from two generator modules, `generate_screener.py` and `generate_exit_strategy.py`, and each is duplicated in `Strategies/Default` (India) and `Strategies/US`. The two copies differ only in the benchmark name used in two prompt sentences. Two other callers reuse the generators as a library. `multi_strategy_utils._load_module()` compiles saved strategy versions for the Multi-Strategy tab and caches them by the hash of the rules text. `sell_screener.load_exit_module()` compiles pinned exit-rule versions the first time they are used. Nothing else in the app touches an LLM: not the event watcher, not the NSE and Nifty utilities, and not Alpaca market data. A replacement therefore has a narrow interface to satisfy: a prompt string goes in and one deterministic Python source string comes out. That is `_client()` plus `_generate_from_prompt()` in the screener generator, and the inline call in `generate_exit_code()`. Each call carries about **4k–6.5k input tokens** and returns about **1k–2k tokens** of Python. Calls are rare and cached, so **correctness matters far more than latency** (sources: `Strategies/Default/generate_screener.py` L192–220, `generate_exit_strategy.py` L12–122, `multi_strategy_utils.py` L179–205, `sell_screener.py` L34–63).

The weak point is what happens after generation. **The repo never validates generated code**: it has no `ast.parse`, smoke run or test file. Code-fence stripping is the only post-processing. Each run overwrites `generated_rules.py` and `generated_exit_strategy.py` with no backup, so a bad generation destroys the last working module. Only Multi-Strategy retries (3 attempts, with 3 s and 6 s backoff). The CLI, the `/jobs` endpoints, `/stats/load-strategy` and `sell_screener` turn a Gemini 503 into a traceback, a non-zero exit, or a holding marked `UNKNOWN`. The prompt also requires blanket `try/except`, so logic errors such as the four off-by-one or wrong-bar bugs from the recent session **fail silently as wrong signals, not as exceptions**. That session is not itself documented in the research notes. Many of the prompt's constraints read like patches for earlier mistakes, for example "index by position with `.iloc`, never `series[i]` on a date index". Any replacement model should be expected to make the same kinds of mistakes.

One configuration bug exists today. **`Strategies/US/.env` does not exist.** The US generators call bare `load_dotenv()`, which searches upward from the script's directory and never reaches `Default/.env`, so US generation probably fails with a missing-key error unless `GEMINI_API_KEY` is set some other way.

## The strong local models don't fit this laptop

The machine is a ThinkPad with a 15 W **i5-1335U, a single 16 GB DDR4-3200 module (likely single-channel, about 25 GB/s), Intel UHD graphics only, and no NVIDIA GPU, CUDA or NPU**. About 6.2 GB of RAM was free when sampled, and C: has about 10.3 GB free. D: has about 114 GB free, so any model files would go there. PowerShell runs in Constrained Language Mode and the user profile belongs to a corporate domain, which points to a managed device where installing Ollama or LM Studio, opening a localhost model server and pulling multi-gigabyte weights may each need IT approval. CPU decoding is limited by memory bandwidth, so the expected speeds follow from bandwidth and model size. A 7–8B model at Q4 should run at about 3–6 tokens/s. A 14B model should run at about 1.5–3 tokens/s, and only with other apps closed. A 32B model does not fit. Counting the time to read a 5k-token prompt, one `evaluate_stock` generation would take roughly **5–10 minutes with a 7B model and 15–25 minutes with a 14B model**. These are estimates from the inventory, not measurements.

The candidates worth running are larger. Qwen's model card reports **Qwen3.6-27B at 83.9 on LiveCodeBench v6 and 77.2 on SWE-bench Verified**, and puts Qwen3.6-35B-A3B at 80.4 and 73.4. Both are Apache-2.0 ([Qwen3.6-27B card](https://huggingface.co/Qwen/Qwen3.6-27B)). Qwen3-Coder-30B-A3B (3.3B active parameters), gpt-oss-20b ("runs within 16GB of memory") and Devstral Small 2 24B are also Apache-2.0 ([Qwen3-Coder card](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct); [gpt-oss-20b card](https://huggingface.co/openai/gpt-oss-20b); [Simon Willison](https://simonwillison.net/2025/Dec/9/devstral-2/)). Their Ollama downloads are about **14 GB (gpt-oss-20b), 15 GB (Devstral Small 2), 17 GB (Qwen3.6-27B) and 19 GB (Qwen3-Coder-30B)**, and the same guide places the 27B and 30B models in the 32 GB RAM tier ([ModelFit](https://modelfit.io/guides/best-local-llm-for-coding/)). On this laptop, with about 6 GB free, gpt-oss-20b's "16 GB" claim describes total memory that is already mostly taken. None of these models runs comfortably here, and the bigger ones do not run at all.

The small models that do fit are a downgrade in exactly the area that matters. Older independent Aider results show how badly mid-size local coders lagged: **Qwen2.5-Coder-32B scored 16.4% and gemma-3-27b 4.9%, against 44.0% for gemini-2.5-flash** ([Aider leaderboard](https://aider.chat/docs/leaderboards/)). A survey of bugs in AI-generated code finds smaller models more bug-prone ([arXiv 2512.05239](https://arxiv.org/pdf/2512.05239)). A 7–8B model working from a 300–550-line numeric spec is likely to produce more off-by-one bugs, not fewer.

### Hardware and approval that would make local codegen viable

A local LLM becomes a credible Gemini replacement on an in-house box with **a 24 GB VRAM GPU** (Qwen3.6-27B dense, fully on the GPU) or **a 16 GB GPU** (gpt-oss-20b fully on the GPU, or a MoE model with light offload). An 8–12 GB card can also work, because llama.cpp's `--n-cpu-moe` expert offload lets 30–35B-A3B MoE models reach a reported **20–47 tokens/s**. Those figures are anecdotal and conflict with one another ([r/LocalLLaMA](https://reddit.sentinel-team.org/posts/1t7l56a/snapshots/2026-05-15T23%3A40%3A01.25497Z); [Medium](https://medium.com/coding-nexus/one-flag-tripled-my-tokens-per-second-on-an-8gb-gpu-238f55d1e3bd)). Without a GPU, **32–64 GB of RAM** can run those MoE models on the CPU at about 10 tokens/s on a desktop i7 ([InventiveHQ](https://inventivehq.com/blog/moe-on-cpu-benchmark)), which is fine for a job that runs once per spec edit. Ollama and LM Studio both expose an OpenAI-compatible endpoint on Windows. vLLM has no official native Windows support ([Ollama docs](https://docs.ollama.com/api/openai-compatibility); [LM Studio docs](https://lmstudio.ai/docs/developer/openai-compat/structured-output); [Docker blog](https://www.docker.com/blog/docker-model-runner-vllm-windows)). Ollama has one known trap: below 23 GiB of VRAM its default context is 4096 tokens, which would **silently truncate a 15k-token spec**, so `num_ctx` or `OLLAMA_CONTEXT_LENGTH` must be set to at least 32K ([particula.tech](https://particula.tech/blog/ollama-num-ctx-silent-prompt-truncation)). On the managed laptop, IT approval would cover the runtime install, a listening localhost port, and model files from Hugging Face or the Ollama registry. An in-house server avoids most of that friction on the owner's machine.

Even the strong-model path keeps one weakness. Research on LLM code errors finds that larger models still get constants and arithmetic wrong ([arXiv 2406.08731](https://arxiv.org/abs/2406.08731v2)), and no study measures pandas index arithmetic against written specs. Moving codegen from Gemini to a local model changes who writes the bug. It does not remove the bug class.

## A rule language removes the off-by-one bug class by design

Every mainstream trading platform resolves "which bar?" with a single offset convention built into the language: Pine's `close[1]`, AmiBroker's `Ref(C,-1)`, Chartink's "1 day ago", and freqtrade's vectorized `shift` ([Pine execution model](https://www.tradingview.com/pine-script-docs/language/execution-model/); [AmiBroker Ref](https://amibroker.com/guide/afl/ref.html); [Chartink](https://chartink.com/articles/author/akash/page/5); [freqtrade](https://www.freqtrade.io/en/stable/strategy-customization/)). **None of them compiles free English into executable logic as the source of truth.** The in-house version of this pattern has five parts. The first is YAML rule files, where each numbered filter in `rules.md` becomes one entry. The second is a small Lark or pyparsing grammar with OHLCV operands, a whitelisted indicator vocabulary (`sma`, `rsi`, `atr`, `highest`, `lowest`), one offset operator in which `close[1]` means one bar ago and negative offsets are a parse error, window aggregates, `crosses_above`, `and`/`or`/`not`, and a `score:` block. The third is a deterministic interpreter that turns `x[n]` into `shift(n)` and `highest(x,n)` into `rolling(n).max()`, and that produces the same boolean series for screening and backtesting. The fourth is a registry of hand-written custom functions such as `@register("cup_handle", ...)` that return typed outputs, so the DSL can reference values like `cup_handle(...).pivot_price`. The fifth is a single `resolve_exit` state machine configured with initial stop, trailing stop, time stop and priority. That last part matches how vectorbt ships stop and trailing exits as library code instead of user code ([vectorbt generators](https://vectorbt.dev/api/signals/generators)). It also removes today's need to keep a generated `resolve_exit` and `describe_state` in sync, because both would read the same engine state.

A purpose-built grammar beats a general expression evaluator. `pandas.eval` lacks shift and rolling, and its own documentation warns about code injection ([pandas docs](https://pandas.pydata.org/docs/reference/api/pandas.eval.html)). simpleeval and asteval both have sandbox-escape CVEs, including asteval's CVE-2026-55244 ([GitLab advisory](https://advisories.gitlab.com/pypi/asteval/CVE-2026-55244/)). The grammar also has a security benefit: the app would stop running freshly generated, unreviewed code in-process, which `stock_screener.py` and `backtest.py` do today.

The costs need to be stated plainly. **Plain-English authoring is lost** unless an LLM-to-DSL aid is kept, so the owner would write YAML expressions the way Chartink and AFL users do. **New custom algorithms need hand-written Python** and their own golden fixtures, for example synthetic cups with known rim indices and pivots that report the bar on which they were confirmed. The existing specs (numbered numeric filters, weighted scores, stop, trail and time-stop with a priority order) fit comfortably in a small grammar, and the pattern detectors are the rare, reusable exception. A DSL alone is still not enough. Platforms with formal languages ship look-ahead tooling anyway, such as freqtrade's lookahead analysis and AmiBroker's warning 1001 ([freqtrade lookahead-analysis](https://www.freqtrade.io/en/stable/lookahead-analysis/)).

The hybrid recovers English authoring. Turning English into a small, grammar-constrained DSL is a much easier task than writing free-form Python. Grammar masking "dramatically" improves syntactic correctness ([arXiv 2407.06146](https://www.arxiv.org/pdf/2407.06146)), and constrained decoding improves semantic accuracy too, with the largest gains for small models ([ACL 2025 Industry](https://preview.aclanthology.org/setup/2025.acl-industry.34)). That makes a 7–8B model on this laptop far more plausible as an authoring aid than as a Python generator. llama.cpp supports GBNF and Lark-like grammars for this kind of constrained output ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). The model can then only make errors of meaning, such as a wrong threshold or a wrong indicator. A deterministic "explain" pass that renders the DSL back into canonical English lets the owner catch those errors before they run. Constraints guarantee syntax, not correctness, so fixture tests stay mandatory ([CRANE, arXiv 2502.09061](https://arxiv.org/html/2502.09061v2)).

Determinism for the local options is limited by llama.cpp itself. Logits are not bit-identical across batch sizes, so prompt caching can change outputs even at temperature 0 with a fixed seed ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)).

## Tests do the work, whoever writes the code

The evidence on generate-test-repair loops is positive but conditional. AlphaCodium raised GPT-4 pass@5 on CodeContests **from 19% to 44%** ([arXiv 2401.08500](https://www.arxiv.org/pdf/2401.08500)). Reflexion reached **91% pass@1 on HumanEval, against an 80% baseline** ([NeurIPS 2023](https://proceedings.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract.html)). LDB added up to 9.8%, which is a maximum rather than a typical gain ([arXiv 2402.16906](https://arxiv.org/abs/2402.16906v6)). Olausson et al. found that once cost is counted, self-repair gains are **"modest" and sometimes absent**, and that the bottleneck is the quality of the feedback ([arXiv 2306.09896](https://arxiv.org/abs/2306.09896)). Every one of these numbers comes from HumanEval-style or competitive-programming benchmarks. None comes from trading code or time-series indexing. The lesson that transfers is that a strong, domain-specific oracle does most of the work.

Seven guardrails apply on any path. The first is an **AST and signature gate**: `ast.parse`, an import whitelist (pandas, numpy, pandas_ta, math, registry), bans on `exec`, `eval`, `open` and network or OS modules, a ban on negative `.shift()` literals and `center=True` rolling ([freqtrade anti-patterns](https://www.freqtrade.io/en/stable/strategy-customization/)), and exact checks on the `evaluate_stock` and `resolve_exit` signatures and return keys. The second is **fixture tests derived from the spec's own numbers**: synthetic OHLCV in which each numbered filter is true at bar T and false at T−1, so an off-by-one fails at the boundary. The third is a **look-ahead truncation test**: evaluating on `df[:t+1]` must equal the full run's result at t, and appending future bars must never change past outputs, which is freqtrade's method ([freqtrade lookahead-analysis](https://www.freqtrade.io/en/stable/lookahead-analysis/)). The fourth is a **repair loop capped at 2–3 attempts** that feeds back concrete diffs (bar index, expected and actual values), then escalates to a human. The fifth is to **keep the previous generated file** and promote a new one only after it passes, running candidates in a subprocess with a timeout. The sixth is a **provider-agnostic client layer**: one `LLMClient` that reads `provider`, `base_url`, `model`, `temperature`, `seed`, `max_tokens` and context size from config. It would use the OpenAI SDK pointed at Ollama (`localhost:11434/v1`), LM Studio (`localhost:1234/v1`) or llama-server, or use litellm with `gemini/` and `ollama_chat/` model strings ([Ollama docs](https://docs.ollama.com/api/openai-compatibility); [LiteLLM docs](https://docs.litellm.ai/docs/providers/ollama)), and strip `<think>` blocks before extracting the code. Gemini's own OpenAI-compatible endpoint was not verified in this research, so litellm is the safer bridge. The seventh is the small fixes: **create `Strategies/US/.env`** or load `Default/.env` explicitly, guard against `response.text` being `None`, add a request timeout, and extend the retry loop beyond Multi-Strategy.

The phasing follows from this. **This week**, add the client layer with Gemini still behind it, the AST and signature gate, backups of the generated files, retries and timeouts on every call path, and the US `.env` fix. **Next**, build spec-derived fixtures and the look-ahead truncation test for the current India and US strategies, and use them as an in-house eval, because no public benchmark covers this task. **Then** build the DSL, interpreter, `resolve_exit` engine and detector registry, porting cup-and-handle, parabola R² and swing-high logic first. Once the existing specs run on the DSL and pass their fixtures, Gemini can be removed entirely. **Later and optionally**, add the grammar-constrained English-to-DSL aid. Run it on the laptop with a small model if IT approves the runtime install, or on an in-house GPU box. Procure a 16–24 GB GPU workstation or a 32–64 GB RAM server only if the owner wants to keep free-form Python codegen.

Several evidence gaps remain. The 2026 model scores are vendor-reported, and the independent Aider board has no entries for Qwen3.6, Qwen3-Coder-30B, Devstral Small 2 or gpt-oss-20b. Tokens/s figures are anecdotal and conflict. Laptop prefill times for 5–15k-token prompts were not measured. No benchmark exists for translating English trading rules into a DSL, and none compares flash-lite with Qwen3.6 on a shared harness.

## Conclusion

The Gemini question is really a correctness question in disguise. The four silent off-by-one bugs came from the architecture, which asks an LLM to choose indexing for each rule and then trusts its output unchecked. Swapping the vendor does not change that. On this laptop, swapping to a local model would make it worse. The durable fix is to move bar-offset semantics out of generated code and into one interpreter that is written and tested once. After that move, an LLM, local or cloud, becomes an optional authoring convenience that sits off the hot path, and the hardware question shrinks from "a GPU workstation to replace Gemini" to "whatever runs a small grammar-constrained model". The guardrails and the provider-agnostic client are worth building this week regardless of the path chosen. They make the current setup safer, they produce the eval needed to judge any local model on this app's own specs, and they keep every later choice reversible through config.
